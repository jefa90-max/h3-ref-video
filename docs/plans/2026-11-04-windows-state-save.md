# Windows 任务状态替换失败

## 证据与边界

- 远端堆栈：RunningHub 返回任务编号之后，`Job.put → Job.save → Path.replace` 抛出 WinError 5；`state.tmp` 已写完，`state.json` 未发布成功。
- `Job.lock` 仅保护当前 Job 内的线程。结果页每 1.4 秒轮询，工作台父进程的 `storyboard.frame_records` / `segments.view` 会普通读取同一个 `state.json`。
- Windows 未启用 FILE_SHARE_DELETE 的打开句柄可阻止重命名/删除；原保存流程未处理这种临时竞争。尚无远端句柄记录，不能断言具体占用进程，也不能排除持续的权限问题。
- 官方参考：https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew

## 最小修复

保留锁、临时文件及原子替换，仅在替换遭遇 Windows 访问拒绝/共享/锁冲突（5、32、33）时有限退避重试。最多尝试 10 次，等待总计 3.25 秒。其它错误立即抛出；重试耗尽继续抛出原始异常，不删除旧状态和待发布的临时状态。文件重试过程不会重新提交云端任务；持续失败后的手动续跑仍需按下文先恢复状态。

不改为直接覆盖 state.json，不删除目标再重命名，不关闭杀毒软件或要求管理员权限。自动从临时文件恢复涉及新旧快照及写入中状态判定，不在本次最小修复中偷偷引入。

## 验证

1. 模拟 5 / 32 / 33 的短暂冲突，验证旧状态持续可读、释放后新任务编号完整落盘。
2. 模拟持续拒绝和非 Windows 错误，验证有界退出、原异常保留、旧状态及 state.tmp 中的已接单编号都未丢失。
3. 生成流程中注入替换失败，恢复后只能轮询同一云端任务，禁止再次提交。
4. Windows 专用测试持有真实目标文件读取句柄，在重试时释放，验证原生文件共享行为；macOS 跳过而非计为通过。
5. 完整离线测试、Python 编译、JS 检查及 Windows 包完整性；不启动用户服务、不调用真实付费接口。

## 现场恢复

先停止该失败任务并备份完整输出目录。核对 state.tmp 和 state.json 中的 segs/frames 任务编号，临时文件可能包含已接单但尚未发布的编号。现有续跑只读取 state.json，还会覆盖 state.tmp；补丁不会自动恢复旧故障遗留的临时文件。未核对并恢复正式状态前，不删除临时文件，不点续跑，也不新建任务重跑。并发段的后续保存可能已经把编号写入正式状态，所以不能盲目用临时文件覆盖正式文件。更新后由用户自行重启 Windows 工作台，确认正式状态保留已接单编号后，从原任务续跑。
