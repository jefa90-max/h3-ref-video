# 视频提交失败的有限重试与续跑

日期：2026-11-02

## 问题和证据

当前整片任务已完成分镜和提示词，但两个视频片段都没有任务号。旧实现将队列/机器繁忙及余额不足统一抛为 QueueFull，film 捕获后每 60 秒无限重试且不记日志。单段入口也没有重试上限。

通过 Context7 查询 RunningHub 官方错误码说明：415 为机器资源不足，421 为并发上限，可等待重试；余额或权限错误不应盲目重试。文档：https://www.runninghub.cn/runninghub-api-doc-cn/doc-8287338 。旧代码兼容的 605/NOT_ENOUGH_BALANCE 同样必须作为终止错误保留原始详情。

## 最小改动

1. 保留 rh.submit 的单次 HTTP 提交，网络异常不自动重复提交，以免重复计费。
2. 两个调用入口共用有限重试函数：最多 5 次提交，前 4 次可重试拒绝后等待 60 秒；逐次打印次数、原始错误与等待时间，耗尽后抛出具体错误。
3. 余额、权限和其他非队列错误立即记录并抛出；新增日志存储为中英文 JSON，工作台按任务语言传给 CLI。
4. 复用已有状态、图片、提示词和已提交任务号；不更改视频轮询或媒体生成参数。

## 验证和恢复

- 离线测试先复现：持续队列拒绝无上限、余额错误误重试、暂时拒绝后的恢复、网络异常不重复提交。
- 验证已有 task 时只轮询不提交；已有分镜/提示词不会再次调用付费生成接口。
- 虚拟环境运行 compileall 和全量 unittest，检查 diff；修复与回归分别 commit。
- 停止原任务子进程前检查本地状态和远端活跃数；保留工作台主进程，通过原任务 resume 接口续跑。
- 前后比较图片和提示词 SHA-256，查看真实错误或视频任务号；若远端余额/权限阻塞，明确报告，不充值或更换账户。
