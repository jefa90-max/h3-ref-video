# ViMax 分镜小样与 RunningHub 首尾帧接口

## 目标与范围

用户确认使用 jobs 里的已有案例，后续明确将范围从图片数量改为 6–8 个分镜。本轮选择《人间善意：三块钱的牛肉骨》第 21–26 镜，生成六镜的首尾帧，最多十二张新图。结果只用于判断下一步是否接入正式流程，不修改应用代码、不生成视频、不启动服务。

原素材：`jobs/2026-11-09_10-26-29/原始/`。该目录的 `脚本.txt` 与任务内 film.json 的 44 个镜头一致；使用用户补齐的场景/道具总表、石磊和周铁林角色图。两张角色图均含初遇期与三年后，当前必须选择初遇期。总表只选择老街肉铺与当前可见道具，不把医院、现代门店、奖状等内容混入画面。

## 首尾关系

同一机位的连续动作可共享边界图片；正常切镜应保持世界状态一致，但可以改变构图、角度与景别。不能为了图片相同而取消原剧本机位。首轮保留第 21–26 镜的不同机位，默认分别生成首尾图；只有文字规划证实可直接复用时才减少调用。

## 借鉴与适配

固定 ViMax 版本 `fd4b72e7731be6e5f88486206d25ea59849b0285`，读取 `agents/storyboard_artist.py` 中的首尾静态画面/动态过程拆解提示和 `interfaces/shot_description.py` 的字段设计。原始文件和 MIT 许可保存在独立试验目录作来源记录，不安装完整 ViMax 依赖。

本次简化：一次整理连续六镜，共享人物、场景、道具状态；沿用当前文字模型和 GPT Image 2.6 图片接口，1K/medium/9:16，每图一个候选。首尾图只输入原始场景与可见角色参考，不恢复全片首镜锚图，也不引入 ViMax 的跨机位过渡视频。该实验检验分镜规划，不能声称完整复刻 ViMax 或证明其参考树策略有效。

旧六张分镜只作可见的历史参考；版本、模型设置和生成时间不完全受控，不构成严格 A/B 实验。

## 执行与检查点

1. 核对原始参考图片、剧本和历史镜头，保存来源与哈希。验证：角色年龄阶段、六个全局分镜号、原文件不写入。
2. 一次文字调用拆出六镜的 `ff_desc`、`lf_desc`、`motion_desc`、机位及起止状态。关键检查点：人工阅读规划后再提交图片。
3. 为每张图保存最终提示词、实际参考图顺序与文件哈希。图片调用最多十二次；提交前保存未知状态，拿到 taskId 立即落盘；失败不自动重新提交、不扩展候选。
4. 目检十二张图片并记录：脸/服装、场景结构、左右关系、袋内道具递增、封口状态、物品交接与动作起止。输出 HTML 对照和 Markdown 结果；清理一次性运行代码，保留输入、任务记录、提示词、费用和生成图。

## 业务验收状态

- 21：空袋开始装肉，尾部已有牛肉，不提前出现骨头/鸡蛋/汤袋。
- 22：起始保留牛肉，结束新增两根牛骨和八颗卤蛋，红袋仍打开。
- 23：保留已有食物，新增两个独立密封汤袋并封好外层红袋；封袋后不要求看见内部食物。
- 24：石磊拿着同一封口红袋走出摊位，内容和体积不重置。
- 25：石磊将同一袋子交至跪地周铁林怀中，不提前让周铁林站起。
- 26：周铁林仍跪着抱袋，抬头看石磊；本镜只改变反应，不再次交袋。

具体精确数量来自用户道具总表，图像是否数得清需独立验收；遮挡时不将不可见物体计为已验证。

## RunningHub 接口结论

标准模型已有 `POST https://www.runninghub.ai/openapi/v2/minimax/hailuo-h3/image-to-video`，字段为 `firstFrameUrl`、`lastFrameUrl`、`prompt`、`resolution`、`duration`，时长字符串 5–15。另有 H3-Max 对应端点。普通网页示例省略图片字段，完整导出规范才包含全部参数。

- [H3 完整规范](https://www.runninghub.cn/runninghub-api-doc-en/api-495380676.md)
- [H3-Max 完整规范](https://www.runninghub.cn/runninghub-api-doc-en/api-509445864.md)
- [调用权限](https://www.runninghub.cn/runninghub-api-doc-cn/)：标准模型仅企业级共享 Key；消费级会员 Key 可走工作流 API。Key 类型不等于必须企业主体，会员积分与共享钱包额度需要分别核对。
- [H3 FL2VA 公开工作流](https://www.runninghub.cn/post/2092500053683433474)：调用前仍需核实实际 workflowId 和导出节点图。现有项目 Ref2VA 工作流不能仅靠追加图片就变成首尾帧接口。

本轮只核查公开 API 文档，没有调用 RunningHub 视频生成或验证其实际费用。Context7 月额度耗尽，改读官方资料。

## 实际执行记录

- 原始资料目录补齐后，使用其中脚本、场景总表、石磊/周铁林设定图，不再使用历史分镜作生成参考。
- 第 25 镜同时写“低角度仰拍”和“石磊视角俯视周铁林”，本次明确采用石磊主观俯视；原脚本保持不变。
- 一次外部文字请求在 TLS 握手阶段超时，没有获得规划响应，不重发；改由本机 Codex 按同一 ViMax 静态拆解提示准备规划。不能将本轮标成外部文字模型或完整 ViMax 流水线跑通。
- 连接复查中 curl 与 Python urllib 都能获得 API 根路径的 HTTP 响应，未证明 Python 传输实现存在持续故障，因此未改正式 HTTP 模块或关闭证书验证。
- 六镜编号和五处首尾世界状态边界已检查；计划、输入和原参考图哈希冻结。输出目录为 `jobs/experiments/vimax-20261109-six-shots/`，单进程、最多两张图片并行、最多十二张新图，无视频请求。

## 首轮结果

十二张图片均成功，实际图片费用合计 ¥2.7639。已逐张目检并独立复核前六张；原始资料、原任务输入与 state.json 哈希不变。

能看到空袋到装肉、加骨蛋、封袋、出摊持袋、交接和跪地抱袋的阶段。历史第 24 镜出摊没有红袋，本轮首尾均持袋。但同镜背景/案板/锅发生变化，21 尾到 22 首肉的外观不稳定，26 尾红袋结扣从上方跑到下方，空间连续性不通过；精确八蛋和封袋内部内容因遮挡未验证。

20 镜取下的毛巾仍挂颈，是规划备注没有进入逐图请求的遗漏，不能全归给模型。本轮只能说明静态起止状态可表达，不能证明完整 ViMax 流程有效，也不能作为已解决连贯性问题的正式功能。

用户提出尾帧应参考本镜首帧。已准备独立 `jobs/experiments/vimax-20261109-tail-guided/requests.json`：保持六张首帧、原始素材、目标尾状态、模型及清晰度，新增本镜首帧作为尾图编辑底图。只需额外六次图片调用，按本轮费用估计约 ¥1.5–2，以供应商实际计费为准。2026-11-09 用户回复“好，做吧”，授权按原清单执行这六次调用，不生成视频。

## 首帧引导尾帧的结果

六张追加尾图全部生成，本轮图片费用按项目汇率折合 ¥1.5626，两轮合计 ¥4.3265。第 21 镜矩形台面、第 22 镜近前景大锅、第 23 镜后景锅和挂钩、第 25 镜过肩交袋构图均比独立尾图稳定，动作阶段也有呈现。已逐张目检，独立复核第 21–23、25–26 镜。

尚未通过的部分：第 26 镜袋扣仍翻至下方；目标描述“牢固结扣和红色褶皱位于下沿”有歧义，可能促成倒袋，但尚无单独对照证明根因。第 24 镜向街面的位移偏小。卤蛋精确数量和封袋内部食物仍因遮挡不能验证。第 25 镜继承首图实际过肩构图，并非纯主观视角。

本轮同时增加首帧参考和编辑指令，没有固定随机种子，只能说明这套做法在样例中更稳；没有重做下一镜首帧，也没有证明跨镜连续性或视频运动已经达标。未追加第 26 镜的额外生成。建议先审定首帧，再编辑本镜尾帧；为道具明确写物体自身朝向，避免用画面下沿代替袋口方向。
