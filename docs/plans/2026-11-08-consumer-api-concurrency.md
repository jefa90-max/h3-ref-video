# 消费级 API 并发与排队恢复

## 问题与边界

用户切换到消费级会员 Key 后，日志显示 5 段同时提交，其中 3 段接收成功、2 段返回 `421 / TASK_QUEUE_MAXED`。当前默认并发为 5，队列拒绝与机器资源拒绝共用最多 5 次提交、4 次 60 秒等待；前一批 H3 尚未完成时，等待中的片段就可能耗尽重试次数。

不能把这段日志解释为消费级只支持串行。也不通过新建任务、重置种子或清除已有云端任务号来解决容量限制。

Context7 查询因本月额度耗尽未取得文档，改查 [RunningHub 官方错误码说明](https://www.runninghub.cn/runninghub-api-doc-cn/doc-8287338)：421 为并发已满，415 为机器资源不足。官网当前新版权益说明将消费级 API 并发上限列为 3；网站任务仍可能占用同一账户额度，旧套餐及现有环境变量可能有不同限制。

## 最小实现

1. 默认 `RUNNINGHUB_CONCURRENCY` 改为 3，仍尊重显式环境变量；同步 `.env.example` 和使用说明。不新增 Key 类型识别、界面设置或账户探测请求。
2. `QueueFull` 保留结构化错误码；421（含已有 `QUEUE_MAXED` 兼容）单独允许最多 31 次明确拒绝，之间等待 60 秒，累计等待最多 30 分钟。
3. 415 保持最多 5 次明确拒绝、4 次等待。两类拒绝分别累计且均有上限，交替出现不能绕过预算；纯 421 最多等待 30 分钟，混合拒绝累计最多等待 34 分钟（不含接口耗时）。日志继续复用双语 JSON 的次数、原因与等待时间占位符。
4. 每次新提交前仍持久保存未知标记，明确拒单后清除；网络结果未知立即停止，续跑禁止自动重提。成功 task 仍先保存再轮询。

## 验证标准

- 先复现连续 6 次 421 后第 7 次可接收却被旧上限提前中止，再验证可成功保存唯一 task。
- 持续 421 达到上限后明确停止、保留资产且可续跑；415 仍为 5 次，混合错误各自预算不重置。
- 第 6 次以后的网络中断仍保留未知标记，下一次续跑不能再提交；已有 task 路径不上传或新建。
- 执行 Python 编译、完整离线 Python / JS 检查；永久 bug 回归保留，临时目录自动清理。既有无关改动保持。
- 不启动／重启服务，不调用真实生成 API，不使用 Claude，不操作原 Windows 任务。修复无法改变已运行子进程；部署后由用户在任务停止后重启并续跑。
